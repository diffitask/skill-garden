# Team status update

- The status-update skill reports merged PRs and currently closed completed issues for an explicit repository and timezone-qualified interval `[since, until)`. End defaults once to current UTC; invalid, reversed or future intervals and missing channel IDs fail before reading APIs.
- Paginate closed repository issue candidates, all currently open PRs and PR reviews with GitHub CLI; read the complete outstanding users/teams from the non-paginated requested-reviewers endpoint. Completion activity uses actual merge/close timestamps in the interval; open PRs are a current snapshot regardless of age. Exclude unmerged closed PRs and not-planned issues. Deduplicate by number and fail incomplete reads without posting.
- Group PR authors, explicitly requested reviewers and submitted review activity by GitHub login, keeping bots visibly identified. A person can appear as author and reviewer, while summary counts count unique PRs. Requested teams stay named as teams rather than guessed members. Completed issues belong to assignees; unassigned issues appear under an explicit unassigned group.
- Author statuses: draft, changes requested, awaiting requested reviewers/teams, current-head approval, changed since approval, discussion without approval, and open without assigned review, in that precedence. Reviewer action lists show only explicit requests for non-draft open PRs. Draft does not prove recent development activity. A current-head approval means an approval exists, never that all branch rules/CI passed or the PR is ready to merge.
- For each reviewer use the latest submitted decisive review (approval, changes requested or dismissal); comments do not erase a previous decision and dismissed approvals never count. Old-head approvals do not approve new commits. Pending reviews are not submitted activity. Merged PR rows show recorded approving reviewers through merge time and the actual merged_by login; no recorded formal approval is stated explicitly. People also see their submitted review activity within the interval, including on PRs merged later.
- Produce one Slack Block Kit message with a header, readable Moscow-time period (configurable IANA timezone), summary counts and divided person sections. Open work and review requests come before completed work. Every item links to GitHub, status is visible beside the item, and a full text fallback supports notifications/accessibility. No-change reports are explicit. Escape untrusted titles, suppress mentions/previews and fail before any write when section/message/block limits would be exceeded; never silently truncate or drop people/items.
- All generated Slack content is in English, including statuses, headings, summaries, empty states, continuation labels and the text fallback. Format dates with the English `en-GB` locale while retaining the configured timezone, independently of the language used to request a report. Keep source GitHub titles and logins intact.
- Dry runs return text and blocks without Slack access. Delivery uses only environment `SLACK_BOT_TOKEN`, verifies an active private channel and bot membership, posts once, and succeeds only on Slack `ok: true` with matching channel and message timestamp. An explicitly configured STATUS_UPDATE_MESSAGE_TS updates that one existing message instead, with no fallback to posting on update failure. Never retry an uncertain write automatically or expose credentials in errors.
- Keep the Air prompt, required environment and activation status in `.air/prompts/status-update.config.md`. Repository files do not create a live automation. Recurring runs require a confirmed schedule/timezone, destination and initial start, serialized delivery and a durable successful end; failures/dry runs never advance that end.
- Integration coverage exercises interval boundaries, every status, author/reviewer/team/assignee grouping, stale/dismissed/comment-only reviews, all pagination, ordering/deduplication, empty/oversized output, Block Kit/fallback parity, dry runs, invalid configuration, private-channel validation and Slack/GitHub failures for both posting and updating. Mocked transport tests do not establish real Slack delivery or Air activation.
